# AlexCyberX security audit — 2026-10-09 (first pass)

Scope reviewed: server/ (index, middleware, payments->removed, alexrecon, alextrace, alexutils, mistake-analyzer),
Supabase public schema (RLS, policies, SECURITY DEFINER functions, cron). NOT yet reviewed: frontend JS (auth.js,
router.js, admin-panel-app.js), lab backends, ai/ routes, attackDetection.

## Fixed in this pass
| # | Severity | Issue | Fix |
|---|----------|-------|-----|
| 1 | Critical | Tool routes trusted `userId` from body/query and used the service-role key (RLS bypass) -> read/write any user's scans, schedules, traces | `requireAuth` in `server/middleware/toolAccess.js` verifies the Supabase Bearer token; userId comes only from the token. Applied to AlexRecon (all routes), AlexTrace, AlexUtils, Mistake Analyzer. Frontend adds the header automatically (top of `js/page-scripts.js`). |
| 2 | Critical | AlexRecon could be pointed at domains resolving to 127.0.0.1 / 10.x / 169.254.169.254 | `assertPublicDomain()` in `alexrecon/modules/utils.js` (DNS-resolves first, blocks private/loopback/link-local/CGNAT). Does not fully stop DNS rebinding. |
| 3 | High (DB) | `get_notifications(p_user_id)` / `mark_notifications_read(p_user_id)` had no `auth.uid()` check; callable by anon -> read any user's notifications | Migration `harden_notifications_and_internal_functions`: caller must equal p_user_id; anon execute revoked |
| 4 | High (DB) | `trigger_due_alexrecon_scans()` callable by anyone via RPC (fires outbound pg_net calls) | execute revoked from public/anon/authenticated (pg_cron runs as postgres) |

| 6 | Low | CORS allowedHeaders lacked Authorization | added |

## Verified OK
- RLS enabled on all 35 public tables; profiles has `protect_profile_privileged_columns` trigger (role/xp/level/ctf_solves/is_banned).
- Admin RPCs (block_ip, save_*, send_broadcast, trigger_manual_backup, ...) contain admin checks.
- No hardcoded secrets (only Supabase anon keys). Static serving is whitelisted.

## Still open (not fixed yet)
1. **CORS `*` fallback** when `ALLOWED_ORIGIN` is unset (server/index.js).
2. **CSP `unsafe-inline` + intentionally vulnerable labs on the same origin as the real app.** Checked the stored-XSS lab: comments are stored per lab session (`X-Lab-Session`, fallback `req.ip`), so a payload only runs for the same player — mostly self-XSS, much lower risk than first assumed. Remaining risks: (a) the `req.ip` fallback means players behind one NAT (hostel Wi-Fi) can share a comment list if the header is missing; (b) a victim tricked into pasting a payload. Longer term, move labs to their own subdomain.
3. `checkToolEnabled` fails open; `uncaughtException` handler keeps the process alive.
4. Admin panel hidden behind a secret URL (obscurity); real protection is RLS/RPC admin checks — keep them tested.
5. pg_cron job `alexcyberx-alexrecon-scheduler` posts to `/api/tools/alexrecon/run-scheduled`, which does not exist; scheduling actually runs in-process (`scheduler.js`). Remove the cron job + `trigger_due_alexrecon_scans` + `app_config.cron_secret` or implement the route.
6. `tool_usage_logs` INSERT policy allows `user_id IS NULL` from anyone (log spam).
7. Remaining SECURITY DEFINER functions are executable by anon by default (PUBLIC grant). Most are harmless/need auth.uid(); review `get_profile_stats(p_user_id)` (public stats by id) and the `blog_increment_views` counter for abuse (`increment_resource_downloads` fixed in step 5b, #47).
8. In-memory lab instances / rate limits are lost on restart and not shared across instances.
9. `ctf_challenges.hints` is selectable by anon/authenticated (flags are NOT — good), so paid hints can be read for free via the API. Unlock text should come only from the `unlock_ctf_hint` RPC; needs frontend change before revoking.
10. `profiles.role` / `is_banned` are public (low risk, but unnecessary).
11. No tests; README is outdated; schema/RLS SQL is not in the repo (export it: `supabase db dump`).

## Step 5a (2026-10-12): security review of tools, community and admin panel
Found by 9 readers + adversarial verifiers; every fix was reproduced before/after and reviewed.

| # | Problem | Fix |
|---|---------|-----|
| 32 | **Critical:** all 12 live CTF flags were hard-coded in `js/admin-panel-app.js` (served publicly under /js, and in the public GitHub repo). | Flags removed from client code. **Open:** rotate the flags and/or make the repo private (they are in git history). |
| 33 | **Critical:** the site-wide attack detector treated normal tool input (`nmap -sV --top-ports`, `O'Brien`, `India@123#`, CVE keywords) as SQL injection and permanently banned the user's IP after 5 requests; it also stored the full input, incl. **plaintext passwords from AlexTrace's password check**, in `security_logs`. | Tool routes are not body-scanned, sensitive fields are redacted, only high-confidence payloads count, logged-in users are never auto-banned, auto-blocks expire after 24 h (`blocked_ips.expires_at`). The live table had no such rows. |
| 34 | **Critical:** stored XSS in the admin panel (page-view device type, contact e-mail in an onclick string, community category/status, CTF scoreboard names): any visitor could run script as the admin. | All DB values escaped / handlers via data attributes; DB whitelists (track_page_view, CHECK constraints, e-mail regex). |
| 35 | **Critical:** AlexRecon SSRF: redirects, script `src` URLs and crt.sh-derived subdomains were fetched without the private-address check (robots.txt of internal hosts returned). SSL checker had no check at all. | Every hop/host re-checked (private, loopback, link-local, CGNAT, metadata, IPv6 ULA, mapped forms); bounded bodies (also decompressed), timeouts. |
| 36 | Banning did nothing (not enforced in RLS, RPCs or the server). | `acx_not_banned()` in community policies, flag/XP RPCs, tool middleware (403 "suspended"); banned users are signed out with a message. |
| 37 | Community: owners could self-pin/unlock, set their vote count, backdate posts; unbounded vote_value; locked threads still accepted replies/votes; no length/rate limits. | Guard trigger, votes only via `vote_thread()`, CHECK constraints, lock enforced, 5 threads / 30 replies per hour. |
| 38 | AlexRecon schedules bypassed every scan limit (direct table writes, no cap, overlapping scheduler ticks), ignored the admin on/off switch and banned users. | Server-only writes, 3 active schedules per user + per-target dedupe, claimed rows, tool switch + bans respected. |
| 39 | Analytics RPCs callable by anyone; CTF Manager writes always failed (no table privilege). | Admin-only RPCs; grants added (flag column still unreadable). |
| 40 | One rate-limit bucket shared by Mistake Analyzer and all AlexUtils endpoints; Gemini calls without timeout; SSL checker did not report trust and showed "Expired: No" in the last 24 h; IP lookup sent domains to an IP-only API. | Per-tool buckets keyed by user, 20 s timeout, trust fields + expiry fixed, domains resolved to a public IP first. |
| 41 | `get_leaderboard()` failed on every call (dropped `badge_count` column): /leaderboard showed "Failed to load". | Recreated, applied. |
| 42 | Found in the final review of the 5a fixes: (a) a 99 KB run of dots in a host field froze the process for ~8 s (quadratic `/\.+$/`), (b) AlexRecon `<title>`/`<script src>` regexes backtracked for seconds on hostile pages, (c) low-confidence detector hits could write unlimited log rows, (d) another site could get a visitor's IP auto-blocked via `<img>` URLs, (e) a suspended user's token still skipped the auto-block, (f) a few special IPv4/IPv6 ranges passed the AlexRecon SSRF guard, (g) crt.sh answers up to 16 MB per scan with no scan concurrency limit, (h) a manual admin block did nothing for an IP with an expired auto-block row. | Length cap + linear trimming, non-backtracking regexes on the page head, 20 log rows per IP per 10 min, cross-site (`Sec-Fetch-Site`) hits logged but not counted, banned = not logged in, one shared IP deny list, 6 MB crt.sh cap + max 2 scans at a time, `block_ip()` makes the block permanent. |
